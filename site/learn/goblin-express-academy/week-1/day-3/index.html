00 · Shift memo

Everything in one shoebox

To:Courier Snag's handler (you) From:Madam Grizzletooth, Proprietor Re:Moving day

Two shifts in, and Snag has a level, a dash and a trail of dust behind him. Good.

Here is the problem. All of it lives in one file: the map, the reviews, the tuning numbers, the controls and the rules. Goblin Express kept its accounts the same way, in one shoebox, until the shoebox caught fire.

Today we move into a proper warehouse, with shelves, labels and a place for everything. The rule for moving day is the rule for every delivery: nothing lost, nothing broken. If Snag plays differently tonight than he did this morning, somebody dropped a box.

— G.

By the end of this module you will

  • Write down what "still works" means before you change anything.
  • Brief Claude on the constraints it can't see for itself.
  • Split the game into files one safe step at a time, with a commit after each.
  • Find an error in the browser and hand it to Claude.
  • Make a change that touches one small file instead of the whole game.

01 · Why one file stops working · 10 min

One shoebox, every parcel

A single file was the right call on Day 1: nothing to set up and nothing to lose track of. Two days later, every change, whether it's a review line, a crate or the dash, happens in the same few hundred lines.

Keeping everything in one file starts to cost you in three ways:

  • Claude reads more than it needs. To change one review, it has to find its way past the map, the controls and the drawing code. That's slower, fills up more of what it can hold in mind at once, and puts unrelated code right next to every edit.
  • You can't review at a glance. Every edit Claude shows you is in index.html. With separate files, the file name tells you whether a "small fix" to the dash also touched the level.
  • Not everyone on a team should touch code. Designers tune numbers, writers edit reviews, level designers move crates. Give each of those its own file and they can work without breaking the game.

If you did Day 2's side quest, Claude's review probably named the single file as a problem. Today deals with it.

§8

Company policyA place for everything. Each file does one job, and data lives apart from code. If you can't say what a file is for in one sentence, it's two files.

02 · Plan the move · 15 min

Measure twice, carry once

Splitting a file without changing what it does is called a refactor. A refactor is easy to judge, because the game should play exactly the same afterward. You only have to decide what "the same" means before anything moves.

1. Start from a save point

Terminal or PowerShell
cd goblin-express
claude
Prompt
Check that everything is committed. If anything isn't, commit it with a clear message so we start the move from a clean save point.

If the move goes badly, this is the commit you send everything back to, just like on Day 2.

2. Write down what "still works" means

Prompt
Before we change anything, read the game and write a checklist of everything a player can see or do, from the start of a shift to the "Shift over" screen: the controls, the dash and its cooldown, the dust and screen shake, the level layout, parcels and the drop-off, scoring, the timer, the reviews and the restart. Keep it short enough to play through in two minutes. Save it as PLAYTEST.md and commit it.

Then play through the list once, on the game as it is now. If something on it doesn't happen, or you notice something the list missed, fix the list, not the game. You'll run this same list after every step of the move. (In Week 3, Claude learns to run it for you.)

§9

Company policyMoving day changes nothing. A refactor moves code around; it never changes what the player feels. Write down what "still works" means before you start, and check it after every step.

3. Brief the move

Claude knows a lot about project structure. What it can't know is how this game gets opened and who will edit it. Put that in the brief:

Prompt
I want to split index.html into a small project with a place for everything, without changing how the game plays. Constraints:

- No libraries, no build step, and nothing to install.
- The game must still start by opening index.html directly in a browser, with no local web server.
- The tuning values, the level map and the customer reviews each get their own file, so someone who doesn't code can edit them.
- Each file does one job.

Tell me the folder layout you'd use, what goes in each file, and the order you'd move things in, starting with the data. Make the steps small enough that I can test each one. Don't change any code yet.

The layout Claude proposes will look something like this:

Example layout
goblin-express/
├── index.html      the page: canvas, score, and the scripts to load
├── style.css       how the page looks
├── PLAYTEST.md     your checklist
└── js/
    ├── config.js   tuning values, each with a comment
    ├── level.js    the Depot text map
    ├── reviews.js  customer reviews
    ├── input.js    keyboard controls
    ├── game.js     the rules: parcels, timer, score, dash
    └── draw.js     everything on screen

Check its answer the way you checked the approach on Day 1. Does it keep every constraint? Did it add anything you didn't ask for, like a framework, a bundler or a package.json? Are the steps small? Push back on anything that's off, in plain words.

Why "no local web server"? Modern JavaScript can split code into modules that load each other, but browsers refuse to load modules, or read data files, from a page you opened by double-clicking. Without that line, Claude may reach for them, and the game goes blank. Later in the course, when Claude starts running the game itself, a local server earns its keep. For now, double-click keeps it simple.

§10

Company policySay what Claude can't see. How the game gets opened, what the team can install, which machines it has to run on: if it isn't in the brief, Claude will guess.

03 · Make the move · 35 min

Moving day

Move the data first, then the code. After each step, play the checklist, then commit. It's Day 2's rhythm, applied to a bigger job.

1. Let the edits through

A move creates a lot of files, and approving each one gets old fast. You've checked the plan and you have a save point, so this is a good time to stop approving every edit. Press Shift + Tab until the status bar under the prompt shows ⏵⏵ accept edits on.

Claude now creates and edits files in this folder without asking. It still asks before running other commands, including Git, and every edit still scrolls past for you to skim. On Windows, if Shift + Tab does nothing, try Alt + M.

2. Move the data

Prompt
Go ahead with the first step only. Then stop, and tell me what to check.

Reload the game in the browser (Cmd + R on a Mac, Ctrl + R or F5 on Windows) and play through PLAYTEST.md. Everything the same? Save it:

Prompt
Commit this step.

3. Move the code

Now the rest, one step at a time:

Prompt
Do the next step, then stop so I can test it.

Play the checklist, commit, and repeat until the plan is done. Five steps means five play-throughs and five commits. That feels slow, but when something breaks, you'll know exactly which step did it.

4. When the screen goes blank

Somewhere in a move like this, something usually breaks: a blank screen, a Snag who won't move, a review that never appears. The browser records why in its console, a panel of messages from the page. Open it:

In Chrome or Edge, press Cmd + Option + J. In Firefox, Cmd + Option + K. In Safari, first turn on Settings → Advanced → Show features for web developers, then press Cmd + Option + C.

In Chrome or Edge, press Ctrl + Shift + J. In Firefox, Ctrl + Shift + K. Or press F12 in any of them and choose the Console tab.

Red lines are errors. Copy them, or take a screenshot of the console like on Day 2, and paste them in:

Prompt
[paste the error] After the last step the screen is blank. This is from the browser console. Fix it without changing how the game plays.

Incident reports

Blank screen, and the console mentions CORS modules opened from a file

Claude split the code into JavaScript modules, which browsers won't load from a page opened by double-clicking. Remind it of the constraint:

Prompt
The game has to start by double-clicking index.html, with no web server. Use plain script tags instead of modules.
The level or reviews won't load, and the console mentions "file" data read with fetch

A page opened from disk isn't allowed to read other files on its own. Ask Claude to keep the map and the reviews in .js files that index.html loads with script tags, rather than in .txt or .json files the code reads.

"… is not defined" scripts load in the wrong order

Plain scripts run top to bottom, in the order index.html lists them. If game.js uses something from config.js, config.js has to come first. Paste the error and Claude will reorder them.

Changing a tuning value does nothing copied, not moved

The old number may still be in two places, and the game is using the other one.

Prompt
Search the project for tuning values that are defined more than once, and make sure each one lives only in the config file.
It's way off, and each fix makes it worse a bad step

Don't patch it (§6). Send it back and redo the step smaller:

Prompt
Put everything back to the last commit. Then redo that step in two smaller pieces, and stop after the first.

5. Check the move with fresh eyes

When the last step is committed, press Shift + Tab until the status bar shows ⏸ manual mode on, the default from Days 1 and 2. Then start a fresh conversation, so Claude sees the project the way a newcomer would:

Prompt
/clear
Prompt
Read this project and tell me in five bullets how it's organized. Then tell me which file you'd open to change a customer review, to move a crate, and to make the dash longer.

Three questions, three different small files? The move worked. /clear doesn't delete anything, by the way: the old conversation is saved, and the project is exactly as you left it.

6. Collect on the move

Now make a change the new shelves make easy. The regulars deserve their own voices:

Prompt
Every parcel is now for one of our regulars: Old Mother Wort, who sends cursed things; the Professor, who orders explosive lab supplies; and Lil' Grub, who keeps ordering live animals. Show who each parcel is for when Snag picks it up, and give each customer their own set of at least five reviews, in their own voice, in the reviews file.

Watch which files Claude opens and edits. It should be a couple of small ones, and the level shouldn't be one of them. Play a shift, then edit one review yourself: open the reviews file in any text editor, change a line, save, and reload the game. That's a writer's whole workflow now, and none of it touches game code.

7. Clock out

Prompt
Commit any remaining changes, then show me today's commits, one line each, and the project's files as a tree.

Compare that log with yesterday's. Every step of the move is its own commit, so if one broke something you didn't catch, you can send back that step alone.

04 · Checkpoint · 5 min

Sign the timesheet

Tick these off. They're saved in this browser only.

Handle With Care

Locked. Finish the checklist to earn it.

Debrief questions

  • What did PLAYTEST.md list that you wouldn't have thought to check?
  • Which constraint did Claude need from you, and what would it have done without it?
  • Which step of the move would you most want to be able to undo on its own?

★ Side quest · optional · ~30 min

Unpack your own game

Run the same move on the game from your Day 1 side quest. Write its playtest list first, then brief the split with constraints of your own: maybe it has to run on the oldest laptop in the studio, or a designer will be editing the enemy stats. Compare the layout Claude proposes with the one it gave you for Goblin Express. Which differences come from your constraints, and which from the game?

Then ask either project a question about the future, without building anything:

Prompt
If we add a second level, which files change, and what would you add? Don't change any code.

A good answer names one or two files. A long list is a sign the move isn't finished.
